# CAD dataset and engineering model v1

This is the foundation for issue #27: a sample's source artefacts become an
engineering model, the engineering model becomes domain models, domain
simulators produce measurements, and the existing V0–V4 contract decides
whether the measurements meet the requirements. Each engineering domain
attaches through a domain adapter (`tools/ecad_model/domains/`); the dataset
runner (`tools/ecad_model/dataset.py`) knows no domain, file format or
simulator. One domain is implemented end to end — mechanical, on
`datasets/cad/robotic_joint_001` — and a test-only adapter for Verilog shows
that a sample with no CAD file runs through the same runner.

```
source/provenance.json ── domain + artefacts ──► the domain's adapter
source/<artefacts> ─► adapter.extract (native parsers isolated) ─► derived/<extraction files>
design/annotations.json ─────────────────────┐            │
                                              ▼            ▼
                                   derived/engineering_model.json
                                              │
        requirements/requirements.json ──┐    ├─► derived/<domain>/…  (mechanical: <item>.mjcf.xml)
                                          ▼    ▼
                      validation/{golden,corners}/cases.json
                                          │
                   existing case engine + the domain's simulator adapter
                                          │
                  receipt.json · evidence/ · results.json · report.md
```

## Separation

| Concept | Where | Owns |
|---|---|---|
| Origin | `source/provenance.json` | Hand-written: the sample's primary domain, its source artefacts by path and format, the script that authored them, where they came from, their licence and attribution, whether redistribution and training use are permitted, and why that is believed. `build` refuses an item without it and never fills it in. |
| Design | `source/<artefacts>` | The source of truth. For mechanical, one STEP assembly: the only source of geometry. |
| Design intent | `design/annotations.json` | What the artefacts cannot carry: which part is which component, materials, joints and their axis sense and limits, components with no geometry. |
| Model | `derived/engineering_model.json` | Everything above, in SI, with provenance on every value. |
| Domain model | `derived/<domain>/…` | The domain's view of the model, for its simulator (mechanical: MJCF for MuJoCo). |
| Simulation | `simulation/*.py` | Produces metrics. Never decides pass or fail. |
| Validation | `validation/*/cases.json`, the V0–V4 contract | Compares metrics against requirements, deterministically. |
| Results | `results.json` of a run | One record per requirement and reference: what was measured against what, on which inputs, by which simulator. |

Everything under `derived/` and `validation/` is generated by
`python3 tools/cad_dataset.py build` and checked by `check`. It is never
edited by hand.

## Quantities

Every engineering value in the model is a quantity:

```json
{"value": 0.544693, "unit": "kg", "status": "DERIVED",
 "source": {"kind": "computation", "ref": "tools/ecad_model/builder.py"},
 "derived_from": ["components/link/geometry/volume", "components/link/material/density"]}
```

| Status | Meaning | Must carry |
|---|---|---|
| `MEASURED` | Observed on a physical artefact. | source kind `measurement` |
| `SPECIFIED` | Stated by a datasheet, a product specification, a requirement, or the design. | |
| `DERIVED` | Computed deterministically from other recorded values. | a non-empty `derived_from` |
| `SIMULATED` | Output of a simulation. | source kind `simulation` |
| `ESTIMATED` | An engineering estimate, not a measurement. | a `note` saying what it rests on |
| `AI_ASSUMPTION` | Proposed by a model. Never presented as `SPECIFIED` or `MEASURED`. | source kind `ai` |
| `UNKNOWN` | Nobody has established it, including "not yet selected". | a `note` saying why |
| `UNSPECIFIED` | The governing source was consulted and is silent on it. | the silent document's `sha256` |
| `NOT_AVAILABLE` | It exists in a source this project cannot access or use. | a `note` saying why |

`UNKNOWN`, `UNSPECIFIED` and `NOT_AVAILABLE` are the null statuses: `value` is
`null` exactly when the status is one of them. Every "is this value missing?"
test in the package goes through one predicate, `quantity.is_null`, so a new
null status cannot slip past one site. The constructors in
`tools/ecad_model/quantity.py` and `engineering-model/v1/common.schema.json`
enforce the same rules, so a hand-written document cannot bypass them.

`DERIVED` is not in the list in issue #27 §35. It was added because a mass
computed as CAD volume × specified density is neither measured nor specified,
and calling it either would misstate it. A mass that cannot be computed,
because its density has a null status, is `UNKNOWN` and still names the
volume and density it would rest on, so the missing density is found from it.
A value from the repository's own product sheets has source kind
`product_specification`: design intent, not a manufacturer's measured data.

## Engineering model

- **Sources**: `design.sources[]`, each `{path, format, sha256}`, where the
  path and format are an artefact the provenance declares. V2 reports a
  model that names an undeclared one.
- **Components** carry `cad_ref` (the STEP part and occurrence), material,
  geometry, mass properties, placement, and per-domain facets
  (`mechanical`, `electrical`, `thermal`, `digital`, …) of quantities. A
  component with no geometry, such as the unselected actuator, has
  `cad_ref: null`.
- **Joints** name parent, child, and the component whose cylindrical faces
  define the axis. The axis line and origin are extracted from that geometry
  and are `DERIVED`; they are never typed in. Non-coaxial or missing
  cylinders make the axis `UNKNOWN`. Geometry fixes a line, not a direction,
  so the annotation's `axis_sense` states which way a positive angle turns.
  The axis is the CAD line oriented to agree with `axis_sense`, and it
  derives from both. An `axis_sense` more than 60° from the CAD line is a
  contradiction, not a hint, and makes the axis `UNKNOWN`.
- **Relationships** form the graph issue #27 §28 asks for: `contains`,
  `mounted_to`, `connected_to`, `drives`, `powered_by`, `controls`, `senses`,
  `attached_to`, `constrained_by`, `thermally_connected_to`.
- **`unknowns`** indexes every null-status quantity by path, sorted, with its
  status and the domains that need it.
- **Lineage**: every `derived_from` entry that names a model quantity must
  resolve, and no quantity may rest, directly or through others, on itself.
  `build` refuses a model whose lineage cannot be followed: an annotated value
  naming a parent that does not exist would leave everything depending on it
  without inputs.

`dataset-item.json` records each of the nine domains with a status in the
words of the specification (§34), plus `NOT_APPLICABLE`:

| Status | Meaning |
|---|---|
| `AVAILABLE` | The sample's primary domain, whose registered adapter validates it from one of the sample's artefacts. It is the only adapter run for a sample. |
| `NOT_APPLICABLE` | An adapter exists but is not run for this sample: the sample has no artefact it reads, or the domain is not the sample's primary domain. |
| `NOT_IMPLEMENTED` | No adapter for the domain exists in this platform. |

The status comes from the platform's adapter registry
(`ecad_model.domains.REGISTRY`), never from the item's data, and `check`
regenerates the manifest to catch a hand edit. Each reason also lists the
null-status inputs the item has for that domain, so a missing motor constant
is reported against electrical even though no electrical adapter exists yet.

The manifest also carries the specification's metadata (§4): `domain`,
`source_url` (from the provenance's origin; `null` only for a self-authored
sample, which the schema enforces), `hash` (a digest of every file git lists
for the sample except the manifest itself), and `versions`: the extraction
producer, `engineering_model`, each domain model's producer, `simulation` (a
digest of the committed simulation scripts, never the simulator's version,
which belongs to a run), and the validation contract. The manifest schema
restates the provenance's licence rules, so it can be checked on its own.

## Requirements

`requirements/requirements.json` holds two kinds of entry. Every entry names
its domain; a sample's entries are compiled by its primary domain's adapter,
and an entry of another domain is refused rather than compiled (cross-domain
rules are later work). Each entry's unit must be its metric's, as the
adapter's metric vocabulary states, and ids are unique across both kinds,
since each becomes a check id.

**Reference values** (V3 golden) verify a domain model against an independent
closed-form derivation computed from the engineering model. The mechanical
derivations:

| Derivation | Closed form | Scenario |
|---|---|---|
| `moving_mass` | Sum of the moving bodies' masses | any |
| `gravity_torque_as_modelled` | Lever-arm cross product about the joint axis | any |
| `small_oscillation_period` | Linearised pendulum, parallel-axis theorem | any |
| `equilibrium_angle` | Rotation about the axis that brings the centre of mass directly below it (`atan2`) | any |
| `min_jerk_peak_speed` | 1.875 · Δθ / T | `rated_move` |
| `min_jerk_peak_accel` | (10/√3) · Δθ / T² | `rated_move` |
| `rated_move_peak_torque` | Peak of \|I·α − τ_gravity(θ)\| over the minimum-jerk profile, sampled every 1 ms | `rated_move` |

A reference may name a scenario. A payload override then applies to the
reference and the simulation alike. These derivations run on a code path
separate from the MJCF writer and the simulator. A frame, unit or
inertia-ordering error in the conversion therefore shows up as a golden
mismatch rather than a silently wrong answer. A gravity with a null status
blocks every derivation that reads it. (The derivations also treat a model
that records no gravity as one they do not apply to, `REFERENCE_NOT_APPLICABLE`;
the mechanical builder always records one, so that arises only for a model
another producer wrote.)

**Requirements** (V4 corner) bound a simulated metric under a scenario, with
`<=` or `>=` and an optional `tolerance`, which is folded into the bound the
contract's comparator evaluates: `<=` becomes a maximum of limit + tolerance,
`>=` a minimum of limit − tolerance. A limit is a number or the path of a
model quantity holding one number. No model decides whether a number
satisfies a limit: the contract's existing comparators do.

Scenario names and their parameters belong to the domain. The generic
requirements schema leaves them open; the mechanical adapter checks every
entry against `engineering-model/v1/mechanical-vocabulary.schema.json`, which
requires what each scenario's case reads (a rated move's start, end and
duration; a free swing's amplitude).

**What an input's status does to a verdict.** A check's inputs are what the
model quantities it depends on ultimately rest on: for a requirement, its
metric's dependencies and its limit when that is a model quantity; for a
reference, the quantities its derivation reads. The mechanical adapter's
dependencies are coarse on purpose: the joint's axis, origin and range for
every metric, and the moving bodies' mass properties and gravity for
dynamics, or every body's bounding box for clearance. The rules apply to V3
and V4 checks alike; applied in order, the first that applies wins:

1. A null-status input makes the check `BLOCKED` with
   `MISSING_REQUIRED_INPUT`, and a finding `<STATUS>: <path>` for each. A
   limit with a null status is not compiled into a case at all.
2. An input that does not resolve in the model makes it `INCONCLUSIVE`
   (`INPUT_NOT_RESOLVABLE`), unless it is already `BLOCKED`.
3. An `AI_ASSUMPTION` input turns the corner comparator's `PASS` or `FAIL`
   on a requirement into `INCONCLUSIVE` (`INPUT_IS_AI_ASSUMPTION`): a value a
   model proposed can neither qualify nor condemn a design. A verdict the
   comparator did not reach — a crash, a missing tool — says nothing about
   the design and keeps its own reason, and a golden, which compares two
   computations on the same inputs, is unaffected.

Every requirement carries a required `illustrative` flag. The example's limits
are `true`: invented to exercise the pipeline, not taken from a customer,
standard or certificate. Meeting an illustrative limit is recorded as
`WARNING` with `WITHIN_ILLUSTRATIVE_LIMIT`, never `PASS`. The contract defines
`WARNING` as advisory: it cannot satisfy a required check, so a sample whose
limits are all illustrative is never eligible for ebuild, however well it
does. Failing an illustrative limit is still `FAIL`. The flag is also carried
into the results and the report.

The v1 receipt contract predates the engineering domains of issue #27 and
classifies checks into six domains. The mapping used is a documented
decision, not an equivalence:

| Engineering domain | Contract domain |
|---|---|
| mechanical, thermal, full_system | `integrated_physics` |
| electrical, digital | `eda_circuit` |
| pcb | `physical_design` |
| power_electronics, electromagnetic | `device_modeling` |
| control | `system_design` |

Cases cite the contract's gate policies (`POLICY:V3-GOLDEN`,
`POLICY:V4-CORNER`), which the v1 requirements catalog defines. The receipt
additionally records the engineering requirement each check implements.

## Validation gates

`python3 tools/cad_dataset.py validate <item> --output <dir>`:

| Gate | Checks |
|---|---|
| V0 `v0.dataset-schemas-and-hashes` | Every dataset document conforms to its schema, including the adapter's extraction files; every recorded hash matches exactly, including provenance, simulation scripts and the licence text; no file is unrecorded; every source a value cites exists. Also `v0.dataset-input-immutability` (inputs unchanged during the run) and `v0.pinned-clean-source` (source tree clean and pinned; its evidence also records where the run happened). |
| V1 `v1.<domain>.extraction-and-sanity` | The sources re-extract, and the domain's sanity checks pass (mechanical: every mass, inertia tensor — symmetric, positive definite, triangle inequality — axis and limit is physically possible). |
| V2 `v2.dataset-reproduction`, `v2.<domain>.model-invariants` | The committed derivation reproduces from the sources, and a committed file that does not parse is a divergence, not a crash; `dataset-item.json` matches the one a rebuild would write; no committed case document is one the requirements no longer compile; every relationship endpoint, requirement subject and design source resolves, and each design source is an artefact the provenance declares. Then the domain's invariants (mechanical: every `cad_ref` resolves to a CAD occurrence, and MJCF bodies correspond one to one with CAD components). |
| V3 | Golden cases, run by the existing case engine and the domain's simulator adapter. |
| V4 | Corner cases, the input-status rules above, and `BLOCKED` checks for requirements whose limit has a null status. A limit met that is illustrative is `WARNING`. |

V1 is classified by what happened, not lumped together:

| V1 outcome | Verdict | Reason code |
|---|---|---|
| No adapter for the item's primary domain is registered | `BLOCKED` | `DOMAIN_NOT_IMPLEMENTED` |
| The parser read the source and refused it (an external reference, a sub-assembly, a mirrored placement, duplicate part names) | `FAIL` | `SOURCE_REJECTED` |
| The parser crashed or produced nothing usable | `INCONCLUSIVE` | `EXTRACTION_CRASHED` |
| The parser exceeded its time limit | `INCONCLUSIVE` | `EXTRACTION_TIMED_OUT` |
| The parser the domain needs is not installed | `BLOCKED` | `EXTRACTOR_UNAVAILABLE` |
| A value the domain model needs has a null status | `BLOCKED` | `MISSING_REQUIRED_INPUT`, a finding `<STATUS>: <path>` for each missing value it rests on |
| The item's inputs cannot be built into a model (a source whose content no importer accepts — a Git LFS pointer, STL, glTF, anything unrecognised — a schema violation, an inconsistent annotation, a requirement that does not compile, or any error the inputs provoke in the builder or adapter) | `FAIL` | `DATASET_INPUT_INVALID` |

**V3/V4 run only on a fresh derivation, and it says what they must hold.**
When V1 derives no model, or the requirements cannot be read, nothing
committed can be trusted to implement the requirements: each reference and
requirement is `BLOCKED` with `DERIVATION_NOT_AVAILABLE` (one gate-level check
stands in when there is none to name, or their ids collide), and no case runs.
When the committed engineering model is missing or not a valid model, each
is `BLOCKED` with `DERIVED_MODEL_NOT_COMMITTED` or `COMMITTED_MODEL_INVALID`.
Otherwise the committed case documents run — their bytes are the evidence —
reconciled with the fresh derivation, which wins where they disagree (V2
reports every such divergence):

- a committed document the fresh derivation no longer produces is not run;
  `build` removes it;
- a committed case for an entry the fresh derivation blocks, or does not
  compile, is not counted; a blocked entry's check says the stale case was
  there;
- an entry the fresh derivation compiles but the committed document lacks is
  `BLOCKED` with `COMMITTED_CASE_MISSING`.

So each reference and requirement has exactly one check. A case document the
engine cannot parse is cited as the evidence of its `FAIL`, which the engine
itself omits. `validate` writes a schema-valid receipt when the inputs cannot
be built into a model, when the requirements cannot be read or compiled, and
when committed derived files have drifted from the inputs or do not parse;
each of these is tested.

**Integrity and reproducibility are deliberately separate.** Hashes in
`dataset-item.json` must match committed bytes exactly. Rebuilding from the
sources must reproduce the committed derived content within a tolerance.
Kernel builds differ in their last floating-point digits across platforms,
and a byte comparison would fail a Linux runner for no engineering reason.
Each derived file declares its comparator. For JSON, a scalar compares within
a relative 1e-9, with an absolute floor of 1e-12, and a vector or matrix
compares with one tolerance scaled by its largest element: a physically zero
product of inertia next to a large principal moment is kernel noise, and
comparing it element by element would call that noise a difference. An XML
domain model compares exactly outside numeric attribute values. A file
declared `exact` compares byte for byte.

The receipt and evidence index are contract documents. They are written the
way the contract serialises them: canonical JSON with one final LF. Evidence
files are stored under `evidence/sha256/<digest>`, and the index records each
file's origin, either a repository path at the pinned commit or the tool that
generated it. `report.md` is for people and is not a contract document.

### Per-requirement results

`results.json` (schema `engineering-model/v1/validation-results`) holds one
result per reference and requirement. Each names the receipt check that
decided it — its own `v3.<id>` or `v4.<id>`, or the gate-level check that
stood in — and its status is that check's verdict. Nothing is filled in: a
result no check decided is an error, not a default. The results are written
after the receipt and the evidence index, so nothing they do can cost a run
its receipt. None are written when no adapter is registered, the requirements
cannot be read, or the committed model is missing or invalid; the report
says which.

| Field | Where it comes from |
|---|---|
| `status`, `reason_code`, `findings`, `evidence` | The deciding check in the receipt; the findings also note a metric that is not a number and inputs that could not be established (the adapter cannot evaluate an entry V1 refused). |
| `measured_value`, `measured_by` | The check's own metric. A V4 requirement `BLOCKED` only because its limit has a null status still reports what another check measured for the same metric with the same arguments, and names that check; no other result borrows a number. |
| `expected_value`, `operator`, `applied_bound`, `tolerance` | The requirement, and the bound as compiled: a V4 minimum or maximum with the tolerance folded in, or a V3 value and absolute tolerance (\|measured − value\| ≤ tolerance, as the golden comparator evaluates it). |
| `simulator`, `simulator_version`, `configuration` | The check's own hash-bound execution record and compiled case (command, scenario, seed); never inferred. The time step is fixed in the domain model, which the case cites as evidence. |
| `model_version`, `model_sha256`, `model_fidelity` | The committed model and the adapter's metric vocabulary (mechanical: `rom_` clearance metrics are `SIMPLIFIED`, bounding-box proxies; the others `EXACT_GEOMETRY`); the fidelity is `null` for a metric the domain does not produce. |
| `inputs` | Every quantity the metric rests on whose status is not `DERIVED`, and every `DERIVED` one with no model inputs, each with its status; plus the scenario's numeric parameters, `SPECIFIED` by the entry that states them. |
| `environment` | The OS, architecture, interpreter and pinned-dependency digest the run recorded in its `v0.pinned-clean-source` evidence, and every tool the receipt records. |

The schema also refuses what the contract forbids: a `PASS` without a
simulator version or a measured value, a `PASS` on an illustrative limit, a
kind that disagrees with the illustrative flag, a result resting on a
null-status input that is not `BLOCKED`, and a comparator verdict on a
requirement resting on an `AI_ASSUMPTION`.

A run's results can be rebuilt from its receipt and stored evidence
(`dataset.regenerate_results`), byte for byte and on any machine, but only
while the item is exactly what the run validated: the item's input digest
must equal the receipt's, and the run must have written results. The run
directory is treated as untrusted: the receipt is schema-checked and must be
for this item, every piece of evidence read must sit at the content address
of its recorded digest and have that digest, an execution record counts only
for the check it belongs to, and a malformed environment record is refused.

## Mechanical model

- Dynamics come only from CAD-derived mass properties: every body carries an
  explicit `inertial`, and `inertiafromgeom` is off.
- Collision geometry is each part's local bounding box. A box contains its
  part, so no contact between proxies soundly implies no contact between
  parts. A reported contact may be a false alarm; a clearance check can never
  pass where the CAD would collide. An L-shaped part would get one box that
  swallows its neighbours, which is why the example base is two parts.
- MuJoCo filters parent–child contacts by default, and the link is nested in
  the base, so `filterparent` is disabled. Excluded pairs come from the
  relationship graph: rigidly attached parts, and the bearing between a
  joint's realizing shaft and the joint's parent. The joint's own
  parent–child pair is never excluded.
- Every dynamics scenario runs with contact disabled, so the proxies can only
  affect the clearance scenario.
- The MJCF writer names every value it needs that has a null status, by model
  path, not only the first; V1 traces each to what it rests on, so a mass
  left unknown by a missing density is reported as the density.

## Security

Source artefacts, the items around them and the run directories validate
writes are untrusted input, and the STEP parser is native code.

- **Process hardening, not a sandbox.** Extraction runs as a child process
  through the repository's hardened `run_process`. The child gets a copy of
  the one STEP file in a throwaway workspace, a scrubbed environment, a 120 s
  timeout, and a 2 GiB address-space limit where the platform enforces it.
  macOS refuses `setrlimit(RLIMIT_AS)` (verified: `ValueError`), and the child
  reports that on stderr. Linux enforces the limit (inferred from standard
  kernel behaviour, not measured here). The parent refuses the result unless
  the child hashed exactly the bytes it was given. Nothing confines the child's
  filesystem or network access, so this protects against a crashing or
  hanging parser, not against a malicious one. The case scripts under
  `simulation/` run the same way and must be authored in this repository,
  never taken from a third-party sample.
- **No external references.** OpenCASCADE resolves a STEP `DOCUMENT_FILE`
  reference by opening the named file during transfer (verified), which
  would read outside the throwaway workspace. The child refuses a file that
  declares `DOCUMENT_FILE`, `EXTERNAL_SOURCE`,
  `APPLIED_EXTERNAL_IDENTIFICATION_ASSIGNMENT` or
  `PRODUCT_DEFINITION_WITH_ASSOCIATED_DOCUMENTS`, and it does so before
  parsing. The scan ignores string literals, so a part named after an entity
  is not refused. After transfer, the child also refuses any result whose
  reader reports an external file. Either refusal is a `SOURCE_REJECTED` FAIL.
- **Only regular files.** Every file is checked with `lstat` before it is
  opened. A FIFO, device or symlink is refused, and so is anything over
  256 MiB. Detection reads content, not the file extension, and names a Git
  LFS pointer as such. Every artefact the provenance declares must exist
  inside the item as a regular file.
- **No symlinks, nothing outside.** Git tracks symlinks. One inside an item
  could redirect a read past the hashes, or redirect a build's write to any
  file the user can modify. `build`, `check` and `validate` refuse an item
  whose directory is a symlink, that resolves outside the repository, or that
  contains a symlink anywhere, before reading it. Each derived-file write also
  refuses a symlink on its path and any target that resolves outside the
  item. A path the manifest records outside the item is reported, never read:
  reading it would make `check` a hash oracle for any file on the host. A
  file cited by hash is read only inside the repository.
- **No silent skips.** An item under a git-ignored path is refused, and so is
  one whose own source artefacts git does not list. Either would otherwise
  make the file list, and every check built on it, silently empty.
- **A run directory is not trusted.** See Per-requirement results: nothing it
  holds is used without its digest verified against the receipt.

## Versioning

`engineering-model/v1` and `cad-dataset/v1` are stable from the change that
added the domain adapters, the null statuses and the per-requirement results.
A compatible addition stays in v1; an incompatible change needs a new
versioned directory, as the V0–V4 contract already requires of itself.

Each producer carries its own version, so a change to one bumps one: the
builder (`builder.VERSION`, recorded as `versions.engineering_model` and the
model's producer), the STEP importer, each domain adapter's derived outputs
(`domains.mechanical.VERSION`), the case compiler (`requirements.VERSION`),
the results generator (`results.VERSION`) and the validator
(`dataset.VALIDATOR_VERSION`, the receipt's `ecad-validator` tool). A
model's `model_version` is the version of the engineering-model document
format; a result also identifies the model by the SHA-256 of its bytes.

## Limitations

- One production adapter: mechanical. The adapter protocol
  (`domains/base.py`) is provisional until the first real second domain uses
  it; the Verilog adapter that exercises it is test-only and validates
  nothing about HDL.
- Only a sample's primary domain is validated. Another artefact in the same
  sample that a different adapter could read is recorded, hashed and marked
  `NOT_APPLICABLE`, but not validated.
- A requirement of another domain is refused; cross-domain rules beyond a
  limit that is a model quantity are not implemented.
- One importer: STEP, through OpenCASCADE. ASCII STL and binary glTF (`.glb`)
  are recognised by content and refused by name; STL carries no assembly.
  Binary STL has no signature and is refused as unrecognised. IGES and native
  formats are not implemented.
- Sub-assemblies are refused; the importer reads one flat assembly level.
- One joint per design, revolute only.
- Materials come from annotations. STEP can carry material data; reading it
  is not implemented.
- The example's requirement limits are illustrative, labelled as such in
  every entry, and are not customer, safety or certification requirements.
- Material densities are `ESTIMATED` nominal values, each with the source of
  the estimate. They are not supplier certificates, so every mass derived
  from them is only as good as that estimate.
- The case engine's execution records are unchanged by this work: a result's
  seed is the compiled case's, and the time step is not a result field.
- Committed derived files come from one platform (macOS arm64). They
  reproduce within the tolerance above on Linux aarch64, where the complete
  suite and `validate` also pass (verified with the adapters in place), and
  under emulation on Linux x86_64 (verified before the adapters were added);
  the MuJoCo stages have not run on native x86_64.

## Adding a domain

A domain is one adapter implementing `domains.base.DomainAdapter`, registered
in `domains.REGISTRY`. The runner calls nothing else:

| Method | What it supplies |
|---|---|
| `domain`, `formats`, `description` | The domain's name, the artefact formats it reads, and what it validates (the manifest's `AVAILABLE` reason) |
| `extract` | The engineering model, and any raw extraction files, from the sample's artefacts; native parsers run isolated |
| `write_models` | The domain model files its simulator runs on, each with its comparator |
| `document_schemas` | The schema of each extraction file, checked at V0 |
| `sanity_problems`, `invariant_problems` | The domain's V1 and V2 checks |
| `case_target` | The existing case engine's tool adapter, the case inputs, and the arguments for a scenario |
| `metrics` | Every metric its cases produce, with its unit and model fidelity |
| `check_requirements` | Refuses scenarios and derivations it does not implement (a vocabulary schema of its own) |
| `reference_value`, `reference_inputs` | Closed-form references for V3, and the model paths each reads |
| `dependencies` | The model paths a metric depends on, for the input-status rules and the results |

The robotic joint's electrical and thermal domains are `NOT_IMPLEMENTED`
today: this platform has no adapter for either. The item would also be missing
their inputs, because the motor is not selected, so its torque constant,
winding resistance and winding temperature limit are `UNKNOWN`. Selecting a

`REQ-XD-001` into a numeric check. The domains themselves still need their
adapters.
